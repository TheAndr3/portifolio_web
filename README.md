# Personal Portfolio & Blog

Welcome to my personal portfolio repository! This project was developed to serve as a central hub to showcase my projects (Showcase) and share technical knowledge through an integrated Blog.

## 🚀 About the Project

This is a Full Stack project developed using the most modern technologies in the React/Next.js ecosystem. The main objective is to consolidate knowledge in hybrid rendering (Server vs. Client Components), performance optimization, and TypeScript best practices.

### Features
- **Portfolio:** Visual presentation of my main projects.
- **Blog:** Dedicated area for articles, tutorials, and texts about technology.
- **Themes:** Full support for Dark/Light mode with user preference persistence.
- **Responsiveness:** Layout adaptable for mobile and desktop devices.

## 🛠 Technologies Used

- **Framework:** Next.js (App Router)
- **Language:** TypeScript
- **Styling:** Tailwind CSS
- **Theme Management:** Next-themes
- **UI Components:** Shadcn/UI (Radix Primitives)
- **Icons:** Lucide React

## 🧠 Learnings and Technical Concepts

During the development of this project, I documented fundamental concepts about how Next.js and modern React work. Below are the key learning points:

### 1. Theme Management (Next-themes)
The `next-themes` library is essential for managing light/dark modes, but it requires specific configurations due to the nature of Server-Side Rendering (SSR):

- **ThemeProvider must be `use client`:** The provider needs to access browser APIs that do not exist on the server, such as `window.localStorage` (to remember the user's choice) and `prefers-color-scheme` (to read the operating system's theme).
- **Global Information:** Just like the theme, data such as "logged-in user" needs to wrap the application (Provider Pattern) so that distant components (like a button in the Header) know the current state without prop drilling.

### 2. Server Components vs. Client Components

#### Server Components (Default)
Next.js renders everything on the server by default. The HTML is generated, converted to a string, and sent ready to the browser.
- **Advantage:** Does not send unnecessary JavaScript for the client to download, resulting in better performance.
- **Strategy:** Keep `layout.tsx` and static pages as Server Components whenever possible.

#### Client Components (`use client`)
They render the initial HTML but then go through the "hydration" process to become interactive. We must use `use client` when we need:
1.  **Interactivity (Event Listeners):** `onClick`, `onChange`, `onSubmit` (e.g., Forms, Action Buttons).
2.  **React Hooks:** `useState`, `useEffect`, `useContext` (e.g., Theme toggle, local states).
3.  **Browser APIs:** Access to `window`, `document`, `localStorage`.

### 3. The Hydration Problem
The **Hydration Mismatch** error occurs when the HTML generated by the server differs from the HTML that React tries to render on the client.
*Example:* The server renders a "Sun" icon (default), but the client reads localStorage and tries to render a "Moon". This difference causes the error.

### 4. TypeScript: Any vs. Unknown
- **Any:** Using `any` is considered a bad practice (and often blocked by ESLint) because it disables type checking, defeating the purpose of TypeScript.
- **Unknown:** If the variable type is not known, `unknown` should be used, which forces the developer to check the type before using it.

### 5. Image Optimization (`<Image />` vs `<img>`)
- **`<img>`:** Standard HTML tag. Loads the entire original file, which can weigh down the site and harm LCP (Largest Contentful Paint).
- **`<Image />` (Next.js):** Native component that automatically converts images to modern formats (WebP/AVIF), resizes on demand, and prevents Layout Shift, ensuring high performance.
